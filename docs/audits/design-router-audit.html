Gesture physics

Your plugin states the principle. apple-design gives the rule a reviewer can check, and adds the warning about CSS transitions.

Yours · design/references/motion.md
Retarget from the currently rendered position. Carry velocity when the animation system supports it. Rapid toggles, reversal, and repeated activation should converge on the latest requested state without snaps, queued animations, or delayed callbacks restoring an old state. During direct manipulation, track input without easing behind it. Preserve the grab offset and support cancellation.
Router · apple-design §3 (Emil Kowalski, MIT)
- Always animate from the presentation (current) value, never the target value. On interrupt, read the element's live on-screen transform and start the new animation from there. - Avoid CSS transitions and @keyframes for anything gesture-driven — they can't be smoothly grabbed and reversed mid-flight. - When a gesture reverses, blend velocity — don't hard-cut it. - Decompose 2D motion into independent X and Y springs.
Not in your plugin anywhere: spring values (move 1.0/0.4, sheet 0.8/0.3), velocity handoff v/(target−current), momentum projection with d≈0.998, the rubber-band formula and ~10px hysteresis. All of them map directly onto SwiftUI springs.

Viewport sweep

Your plugin says to check breakpoints. viewports defines the sweep, so a skipped check shows up as a finding.

Yours · references/evidence.md
Include a narrow viewport for responsive work, and use 320px when supported or requested. Check affected breakpoints and unintended horizontal overflow; wide content should scroll within its own container. An untested width remains a coverage gap rather than an implied pass.
Router · viewports (Raphael Salaja, MIT)
The widths are exact: 320, 375, 768, 1024 and 1440, plus 1px either side of each project breakpoint. A width reasoned from the media queries is a finding. … 4. Tap at touch widths — a delete button that shows only on row hover is viewports-no-hover-only-controls. 5. Shorten the height — Render 812×375. Open each dialog, sheet and menu at that size. 6. Double the text
A native block is needed: the smallest and largest iPhone, iPad Split View and Slide Over, landscape, Dynamic Type from xSmall to AX5 (the native version of 200% text), and the macOS minimum window size. overflow.js only runs in a web page.

Removing motion

Your plugin can review and add motion but has no mode for taking it out. remove-animations lists what breaks when you delete an animation.

Yours · nearest is references/craft-floor.md
No routine bounce/elastic motion, identical fade-up entrances on every section, or hover lifts on every card. Keep content visible before motion and make any expressive motion belong to the chosen direction.
Router · remove-animations Removal Hazards (Emil Kowalski, MIT)
- Hidden start states. … Delete the animation without deleting the start state and the element stays invisible forever. - Code that waits for the animation. transitionend listeners … setTimeout calls sized to a duration. - Exit animations that delay unmount. - Layout animations hiding a jump. Remove it and the jump appears. - Focus timed after motion. - Tests and selectors.
Fork at the seams: keep the six hazard names and their consequences verbatim. Move AnimatePresence and onExitComplete into a labelled web example, and add the SwiftUI case: a .transition holding a view during removal, and a withAnimation completion.

Writing the forks to the skill guidelines

From your skill creator and OpenAI's Rethinking skills and prompts for GPT-6. A verbatim fork keeps the rules; these seams keep the forks short.

The root file only routes

The article's phrase is "make the root document a minimal router." Forked text goes into references and never into SKILL.md. design-to-motion (519 lines) should become a short router over three files: Part A fidelity, Part B motion, Part C capture.

SKILL.md holds A1–C2, a 40-item checklist and output format
SKILL.md: two contexts + "Read references/fidelity.md before touching motion"

Descriptions name triggers, not catalogs

All 7 descriptions run 221–267 characters and list many nouns. The article says descriptions "should be as short as possible", with specific triggers that don't overlap.

design: "…UI design, product idea evaluation, visual exploration, UX copy or microcopy, button and error-message wording, motion terminology, and developer handoff…"
design: "Design, build or refine web and native product UI. Use for new screens, redesigns, variants, recreating a reference, UX copy and handoff specs."

Strip the persona and the absolutes

Emil's skills open with an "Initial Response" greeting, and several say "No approximated values" or "Never present motion options as a menu." Cut them at the seam. Keep the values, labelled as starting points, as your motion.md already does.

"When this skill is first invoked … respond only with: I'm ready to help…"
(removed; the skill starts at its first rule)

Rule IDs label findings; they don't make rules stricter

Raphael's broken/replacement pairs (viewports-short-heights) give a reviewer a concrete example to apply. Keep them in review references, where findings cite them. Leave them out of build guidance, where they turn into a rigid checklist.

Rule IDs on every build instruction in defaults.md
Review finding: "Save is off-screen at 812×375 [viewports-short-heights]"

Only stop where the user has a real choice

The article warns that "a requirement to stop for review" makes the model stop early. Keep the stops where the user genuinely decides, such as picking a variant or choosing which fixes to apply. Drop the stops in improve-animations' plan step and Raphael's audit gate.

"Stop. Wait for the user to choose before writing plans."
Number the findings; apply the ones the user picks, or all of them when the request asked for fixes.

Point to references only when they are needed

design-review currently says "read the full critique guide … the full accessibility guide … the full UX-copy guide". New references should be linked from the routing tables only, with each link saying when to read it.

"For accessibility, read the full accessibility guide."
"Keyboard walk → accessibility.md#keyboard-walk, when focus or shortcuts changed."
