# Refactoring

**You own the contract. The structure changes. The behavior does not.** Distinct from Feature, which adds behavior, and Bug fix, which corrects it.

If the cleanup reveals a missing feature or a real bug, report it separately and complete the structural change against the pinned contract. New behavior requires authorization; route it through [Feature Development](../references/feature-development.md). For large or cross-cutting structural work, use that workflow's planning handoff when a plan is requested. This playbook owns the behavior-preserving work.

1. Pin the behavior contract first. Use [How](../skills/how/SKILL.md) when the contract is unclear, then choose the pin for the change. For a mechanical rename or move, use reference searches and the type checker where they cover the affected usages; check dynamic references and runtime paths only where those tools cannot establish equivalence. For a structural redesign, use an existing check or write a characterization test, snapshot, or equivalence harness that captures current behavior before any structure moves.
2. For a structural redesign, name the structure the code is missing using [Model the domain in data](../references/engineering-principles.md#model-the-domain-in-data). Boring code stays when the shape is already clear and local. Prefer a reshape that deletes branches or invalid states without adding indirection.
3. Use the user-specified target when given. Otherwise name the target shape: what the module layout, types, and call graph should be if built today, starting from the current requirements and data shape. Use [Architect](../skills/architect/SKILL.md) when a consequential boundary, contract, or state decision must be settled before the move.
4. Subtract before you add. Delete dead code, collapse one-caller wrappers, drop redundant validators, and remove orphan references before introducing the new shape within the requested scope. The smallest change that reaches the target shape ships. A speculative cleanup that "might help" gets reverted.
5. Move in small behavior-preserving steps, each keeping the pin green. For API reshapes, migrate every caller and delete the old API in the same wave under [Hard-cut policy](../references/hard-cut-policy.md), including its external-compatibility and staged-rollout exceptions. Spot-check every rename against the actual files. Renames silently miss usages in strings, prose, and back-references. When delegation helps and the host permits it, give mechanical edits to a worker with a specific scope (file paths, the names being moved, the behavior to hold). Use the host's configured model policy.
6. Use the pin to establish unchanged behavior. For larger reshapes, run an equivalence check: a script that diffs old-vs-new outputs, a recorded baseline replayed against the new code, or a smoke run on the matching surface using the repository's verification skill, existing harness, or available app-control tool.
7. Confirm the change is worth keeping. The success measure is reduced reader load as described in [Engineering principles](../references/engineering-principles.md#pass-the-30-second-reader-test). If a reshape you chose does not lower reader load somewhere, revert it. For a user-specified target, report the delta rather than undoing the requested change.
8. When commits are requested, use small ordered commits under the repository's conventions. A subtraction commit, then the reshape, then any follow-on cleanup. Each behavior-preserving slice stays green before the next. Finish under [Feature Development](../references/feature-development.md#completion); run [Publish PR](../skills/publish-pr/SKILL.md) only when publication is requested.

Write the report with [Writing style](../references/writing-style.md).

**Reply:** the structure that changed, the pin you held it against, the equivalence proof, the reader-load delta, what shipped and what got reverted. No new behavior.
